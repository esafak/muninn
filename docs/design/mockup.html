How it works

  • Extract & infer — every message (user + assistant, incl. tool output) is scanned for shorthand (PR #4821, #1043, run #18402) and URLs. Shorthands resolve against the repo inferred from the session's git remote, so "PR 123" contextualizes itself.
  • Associate — issue ↔ PR via closing keywords ("Closes #1043") or branch match; PR ↔ run via head SHA / check-suites. The triplet (issue, PR, runs) is one history card.
  • Chronology — cards sort by last activity, newest first, grouped by day. A card's internal runs list is newest-first too. CI state changes (queued → running → failed/succeeded) update the card in place and float it to the top.
  • Pills — one pill per chain, PR/CI first: #4821 · e2e failing ⇢ #1043 +1. Linked issues collapse to a +N in the label; the dropdown always shows every member (PR, runs, checks, all issues). Worst chain first, capped at three. Zero chains → zero pills.
  • Merge — a green Merge pill beside the chain pill (and a button on the sidebar card): green = mergeable + all checks passed + no outstanding reviews; amber = pending; grey = blocked with reasons on hover. Its dropdown holds method (merge / squash / rebase, repo-limited), Delete branch (default on), Delete worktree (opt-in, skipped politely on uncommitted changes), and Merge when ready — arming turns the pill amber and re-picking cancels; the merge fires on readiness, guarded by the expected head SHA. Drafts and read-only credentials get no control.
  • Providers — one narrow interface; GitHub first (REST via gh credentials). GitLab/Jira/Linear later swap in behind the same interface; UI only renders generic kinds (issue / pr / run).

Provider interface (narrow, swappable)

type Kind = "issue" | "pr" | "run"
type RunStatus = "queued" | "running" | "succeeded" | "failed" | "cancelled"

interface SourceProvider {
  id: string            // "github" — provides the mark glyph
  repo(directory: string): Promise<RepoRef | undefined>
  // { host, owner, name, branch } from the git remote

  scan(text: string, repo: RepoRef): SourceRef[]
  // extract + infer: ("PR #4821" | "#1043" | url) → ref

  get(ref: SourceRef): Promise<Entity | undefined>
  // hydrate: { kind, id, title, state | runStatus, url, … }

  related(entity: Entity): Promise<SourceRef[]>
  // association: issue↔pr, pr↔runs
}
  • UI renders only Kind + status + mark — it never knows GitHub specifics.
  • Polling cadence lives in the plugin's server part; the GUI is a view over hydrated entities.

Decisions (settled)

  • Placement — pills above the composer (ComposerPill slot). The footer strip (window.bottom) remains in the toggle above for reference only.
  • Pill grouping — one pill per chain, PR/CI first. Linked issues collapse to +N in the label and always appear in full in the dropdown. Several PRs on one issue stay rows of the same pill, led by the session's own branch match.
  • Merge button — Merge pill in the composer row + button on the sidebar card; readiness-colored (CI × reviews × mergeability); dropdown holds method (only when the repo allows more than one — single-method repos merge in one pick, no ask), delete-branch/worktree toggles, and merge-when-ready (armed = amber pill, re-pick cancels); head-SHA race guard; write-access gated.
  • History shape — triplet cards; association is structural, chronology at card level, most recent activity first.
  • Naming — forgescout · tab "ForgeScout". Provisions and tracks what the session ships: PRs, issues, CI runs.
  • Run scope — runs tied to session-linked PRs/issues, plus branch-push runs on the session's branch.
  • Cross-session — v1 is per-session history; project-wide roll-up deferred.
